# 영호 가챠 시즌 초기화 설계

## 목적

관리자 한 명이 영호 가챠의 모든 플레이어 진행도와 활동 기록을 안전하게 초기화할 수 있게 한다. Discord 계정과 현재 로그인 상태, 카드 콘텐츠, 세트 효과, 확률, 지급 설정 등 관리자가 구성한 게임 설정은 그대로 유지한다. 이 기능은 운영 데이터에 직접 영향을 주는 파괴 작업이므로 영향 미리보기, 강한 확인 절차, 동시 요청 차단, 단일 트랜잭션 및 회귀 테스트를 필수로 한다.

이 설계는 실제 시즌 번호나 과거 시즌 열람 기능을 도입하지 않는다. 현재 요구사항에서 “시즌 초기화”는 기존 진행 데이터를 실제로 삭제하고 같은 게임 설정으로 새 출발시키는 관리 작업을 뜻한다.

## 확정된 제품 결정

- 카드, 세트, 확률, 일일 지급량, 신규 사용자 혜택 등 모든 관리자 설정값을 보존한다.
- 사용자 계정과 현재 로그인 세션을 보존한다.
- 인벤토리뿐 아니라 영구 해금으로 취급되던 도감도 초기화한다.
- 기존 사용자는 초기화 직후 현재 `신규 사용자 혜택` 설정만큼 추가 뽑기권을 다시 받는다.
- 초기화 당일의 `매일 기본 지급`도 즉시 사용할 수 있다.
- 기존 관리자·확률 감사 로그를 포함한 과거 로그를 모두 삭제한다.
- 삭제 후 실행 관리자, 실행 시각, 삭제 건수를 담은 시즌 초기화 감사 기록 한 건만 새로 남긴다.
- 초기화 도중 실패하면 삭제나 재지급이 일부만 반영되지 않도록 전체 작업을 롤백한다.
- 배포나 테스트 과정에서 운영 초기화를 자동 실행하지 않는다. 관리자가 UI에서 직접 확인한 경우에만 실행한다.

## 데이터 경계

### 보존 대상

| 테이블 또는 데이터 | 보존 이유 |
| --- | --- |
| `users` | Discord 신원, 사용자명, 프로필, 첫 로그인 경고 확인, 선물·거래 허용 설정을 유지한다. |
| `web_sessions` | 현재 로그인 상태를 유지한다. |
| `oauth_attempts` | 초기화 순간 진행 중인 Discord OAuth 인증을 중단하지 않는다. |
| `rarity_settings` | 관리자가 설정한 1~5성 확률을 유지한다. |
| `cards` | 카드 이름, 이미지, 등급, YP, 가중치, 활성 상태를 유지한다. |
| `card_sets`, `card_set_members` | 세트와 구성 카드를 유지한다. |
| `set_effects`, `set_effect_target_cards`, `set_effect_bonus_target_cards` | 모든 세트 효과 규칙과 대상을 유지한다. |
| `draw_settings` | 매일 기본 지급량과 신규 사용자 혜택 설정을 유지한다. |
| `image_cleanup` | 이미 예약된 이미지 정리 작업을 유실시키지 않는다. |
| `alembic_version` | 데이터베이스 마이그레이션 상태를 유지한다. |

카드 이미지 파일도 삭제하지 않는다. 초기화 구현은 DB 스키마, 반디봇 JSON 메모리, 봇 대화 기록 및 다른 Railway 서비스의 데이터에 접근하지 않는다.

### 삭제 대상

| 분류 | 테이블 |
| --- | --- |
| 플레이어 자산 | `inventory`, `catalog_unlocks` |
| 뽑기 진행 | `draw_states`, `draw_wallets`, `daily_draw_allowances` |
| 뽑기 기록 | `draw_batches`, `draw_history`, `five_star_events` |
| 자산 이동 기록 | `gifts`, `discard_events` |
| 거래 | `trade_rooms`, `trade_offers`, `trade_requests` |
| 전달·접속 임시 데이터 | `notification_outbox`, `websocket_tickets` |
| 과거 감사 로그 | `probability_audit`, `admin_audit` |

삭제 대상은 코드의 명시적 허용 목록으로 관리한다. DB 전체 `DROP`, 스키마 재생성 및 `TRUNCATE ... CASCADE`는 사용하지 않는다.

## 초기 지급 규칙

삭제 작업으로 모든 `draw_wallets`와 `daily_draw_allowances`를 제거한다. 이후 보존된 `draw_settings.new_user_bonus_tickets`가 0보다 크면 모든 기존 사용자에 대해 해당 수량의 `draw_wallets` 행을 새로 만든다. 이 지급은 시즌 초기화 트랜잭션 안에서 정확히 한 번 실행한다.

`draw_history`와 당일 보정 행이 없어지므로 모든 기존 사용자는 현재 KST 뽑기일에 설정된 `draw_settings.daily_draws`를 즉시 사용할 수 있다. 신규 가입 혜택 설정 자체는 변하지 않으므로 초기화 이후 처음 가입하는 사용자도 기존 가입 흐름에 따라 같은 혜택을 받는다.

## 백엔드 구조

### 시즌 초기화 서비스

새 `bandi_cards/services/season_reset.py`가 다음 두 동작을 담당한다.

1. `preview_season_reset(db)`
   - 각 삭제 대상 테이블의 현재 행 수를 읽는다.
   - 보존될 사용자 수, 카드 수, 세트 수, 확률 및 지급 설정의 존재 여부를 함께 반환한다.
   - 데이터를 변경하지 않는다.

2. `execute_season_reset(db, admin_id)`
   - PostgreSQL 트랜잭션 수준 advisory lock으로 동시에 한 번만 실행되도록 한다.
   - 외래키 순서에 맞춰 삭제 대상 테이블을 명시적으로 삭제한다.
   - 신규 사용자 혜택을 기존 사용자 전원에게 재지급한다.
   - 이전 `admin_audit`를 삭제한 뒤 `season.reset` 감사 기록 한 건을 생성한다.
   - 감사 상세에는 삭제 전 행 수, 재지급 사용자 수와 장수, 보존된 설정 확인값을 JSON으로 남긴다.
   - 호출자가 한 번만 커밋하며 서비스 내부에서 부분 커밋하지 않는다.

SQLite 테스트에서는 같은 서비스 경계를 사용하되 PostgreSQL 전용 advisory/table lock 문장만 생략한다. 삭제·재지급·감사 동작은 두 DB에서 동일해야 한다.

### 관리자 API

새 `bandi_cards/routes/admin_reset.py`를 추가하고 앱에 등록한다.

- `GET /api/admin/season-reset/preview`
  - `SPECIAL_USER_ID` 관리자만 접근한다.
  - 삭제 및 보존 항목별 수량을 반환한다.
- `POST /api/admin/season-reset`
  - 관리자 세션과 CSRF 토큰을 모두 검증한다.
  - 본문의 확인 문구가 정확히 `영호 가챠 시즌 초기화`인지 확인한다.
  - 초기화가 이미 진행 중이면 `409 Conflict`를 반환한다.
  - 성공 시 삭제 건수, 재지급 결과 및 완료 시각을 반환한다.

API는 확인 문구 오류에 `400`, 권한 오류에 `403`, 초기화 중 일반 변경 요청에는 `503`과 사용자용 메시지 `시즌 초기화가 진행 중입니다. 잠시 후 다시 시도해주세요.`를 사용한다.

## 동시성 및 유지보수 경계

현재 Railway 웹 서비스가 단일 인스턴스로 운영되고 실시간 거래 역시 단일 인스턴스에 제한된다는 기존 결정을 따른다.

앱에 `SeasonResetCoordinator`를 두어 안전하지 않은 카드 도메인 요청의 진행 개수를 추적한다. 초기화가 시작되면 다음 순서를 지킨다.

1. 관리자 초기화 요청을 제외한 신규 POST·PUT·PATCH·DELETE 요청을 `503`으로 차단한다.
2. 이미 들어온 변경 요청의 진행 개수가 0이 될 때까지 기다린다.
3. DB advisory lock을 획득하고 삭제 대상 테이블을 잠근다.
4. 시즌 초기화 트랜잭션을 실행한다.
5. 성공 또는 실패 여부와 관계없이 유지보수 상태를 해제한다.

프로세스가 트랜잭션 도중 종료되면 DB가 전체 작업을 롤백하고, 프로세스 메모리의 유지보수 상태도 재시작과 함께 해제된다. PostgreSQL advisory lock은 중복 관리자 요청이 같은 작업을 두 번 실행해 혜택을 중복 지급하는 것을 방지한다.

반디봇 알림 소비자와 동시에 실행될 수 있으므로 `notification_outbox`를 잠근 뒤 삭제한다. 이미 Discord 전송 단계에 들어간 극히 드문 알림은 회수할 수 없지만, 아직 DB에 대기·재시도 중인 초기화 전 알림은 모두 제거한다.

## 실시간 연결 처리

초기화 성공 후 `ConnectionManager`가 모든 열린 WebSocket에 다음 이벤트를 보낸다.

```json
{"type": "season.reset"}
```

클라이언트는 이 이벤트를 받으면 열려 있던 거래 상태를 폐기하고 메인 화면으로 이동한 뒤 사용자·인벤토리·도감·랭킹·뽑기 상태를 다시 불러온다. 이미 발급된 `websocket_tickets`는 삭제하므로 이후 재연결은 현재 로그인 세션으로 새 티켓을 받아야 한다.

실시간 통지는 커밋 이후에만 보낸다. 통지 실패는 성공한 DB 초기화를 롤백하지 않으며, 연결이 끊긴 사용자는 다음 HTTP 조회에서 새 상태를 확인한다.

## 관리자 UI

관리 페이지 최하단에 기본적으로 접힌 `위험 구역`을 추가한다. 기존 관리 버튼처럼 사용자가 펼치기 전에는 실행 컨트롤을 노출하지 않는다.

1. `초기화 대상 확인` 버튼을 누르면 미리보기 API를 호출한다.
2. 삭제될 인벤토리 수량, 도감 해금, 뽑기 기록, 5성 로그, 선물, 버리기, 거래, 알림 및 감사 기록 건수를 표시한다.
3. 보존되는 사용자·카드·세트 수와 현재 매일 지급량·신규 혜택 수량을 별도 영역에 명시한다.
4. `되돌릴 수 없습니다` 경고와 함께 확인 입력칸을 보여준다.
5. `영호 가챠 시즌 초기화`가 정확히 입력되기 전에는 실행 버튼을 비활성화한다.
6. 실행 중에는 버튼을 다시 누를 수 없게 하고 진행 상태를 표시한다.
7. 성공하면 삭제·재지급 요약을 보여주고 현재 관리자 세션을 유지한 채 메인 화면 데이터를 새로 불러온다.
8. 실패하면 서버 메시지를 표시하며 미리보기 화면을 유지해 관리자가 다시 판단할 수 있게 한다.

브라우저 기본 확인 팝업에 의존하지 않고 모든 경고와 확인 절차를 페이지 안에서 처리한다.

## 감사 기록

초기화 전에 존재하던 `admin_audit`와 `probability_audit`는 요청대로 삭제한다. 같은 트랜잭션의 마지막에 다음 정보를 포함하는 단일 `AdminAudit` 행을 생성한다.

- `action`: `season.reset`
- `target_type`: `season`
- `target_id`: 완료 시각 또는 초기화 요청 식별자
- `admin_id`: 실행한 관리자 사용자 ID
- `details_json`: 테이블별 삭제 건수, 재지급 사용자 수, 사용자당 추가권 수, 총 재지급 장수, 보존 설정 확인값

이 기록은 초기화가 실제로 수행됐다는 최소한의 운영 증거이며 다음 시즌 초기화 때 이전 로그로서 삭제되고 새 기록으로 교체된다.

## 오류 처리

- 미리보기 실패는 어떤 상태도 변경하지 않는다.
- 확인 문구, 관리자 권한 또는 CSRF 검증 실패 시 DB 작업을 시작하지 않는다.
- advisory lock 획득 실패 시 중복 실행을 거부한다.
- 삭제, 재지급 또는 감사 생성 중 예외가 발생하면 트랜잭션 전체를 롤백한다.
- 롤백 후 유지보수 상태를 반드시 해제한다.
- 실시간 알림 실패는 로그로 남기되 이미 커밋된 초기화를 실패로 표시하지 않는다.
- 보존 대상 설정 행이 없거나 유효하지 않으면 초기화를 시작하지 않고 관리자가 먼저 설정을 복구하도록 안내한다.

## 테스트 전략

운영 DB에서는 자동 초기화를 실행하지 않는다. 모든 삭제 검증은 외래키가 활성화된 격리 SQLite DB와 필요한 PostgreSQL 통합 경계에서 수행한다.

### 서비스 테스트

- 미리보기가 모든 삭제 대상 수량과 보존 대상 수량을 정확히 반환한다.
- 실행 후 삭제 허용 목록의 모든 행이 0개가 된다.
- `users`, `web_sessions`, `oauth_attempts`, 카드·세트·확률·지급 설정 및 이미지 정리 작업이 동일하게 남는다.
- 모든 사용자에게 현재 신규 사용자 혜택이 정확히 한 번 재지급된다.
- 혜택이 0이면 불필요한 지갑을 만들지 않는다.
- 현재 일일 기본 지급분을 즉시 사용할 수 있고 천장은 0에서 시작한다.
- 과거 감사 로그가 사라지고 `season.reset` 한 건만 남는다.
- 주입된 중간 실패가 모든 삭제와 재지급을 롤백한다.

### API·권한 테스트

- 비관리자는 미리보기와 실행 API에 접근할 수 없다.
- CSRF 누락과 잘못된 확인 문구를 거부한다.
- 동시에 온 실행 요청 중 하나만 성공한다.
- 초기화 중 다른 변경 요청은 `503`으로 거부된다.
- 성공 응답의 수량이 실제 변경 결과와 일치한다.

### UI·실시간 테스트

- 위험 구역은 기본적으로 접혀 있다.
- 미리보기 전에는 확인 입력과 실행 버튼이 나타나지 않는다.
- 정확한 문구가 아니면 실행 버튼이 비활성화된다.
- 중복 클릭을 막고 성공·실패 상태를 명확히 표시한다.
- `season.reset` 이벤트를 받으면 열린 거래 화면을 닫고 주요 데이터를 다시 불러온다.

### 전체 회귀 테스트

- 초기화 후 뽑기, 10회 뽑기, 도감, 인벤토리, 랭킹이 빈 진행 상태에서 정상 동작한다.
- 선물과 거래는 새로 획득한 카드로 다시 사용할 수 있다.
- 기존 사용자는 로그아웃되지 않는다.
- 초기화 이후 새 가입자는 설정된 일일 지급과 신규 사용자 혜택을 정상적으로 받는다.
- 반디봇의 가챠·랭킹 명령과 프로필 동기화가 보존된 계정 및 새 랭킹 상태를 사용한다.

## 배포 및 운영

- 스키마 추가가 필요하다면 먼저 하위 호환 마이그레이션을 배포한다. 현재 설계는 시즌 번호 보관을 요구하지 않으므로 가능하면 기존 테이블과 앱 상태만 사용한다.
- 배포 후 관리자 미리보기 API가 운영 데이터를 변경하지 않는지 먼저 확인한다.
- 실제 초기화는 관리자가 삭제 건수와 보존 설정을 확인하고 직접 실행한다.
- 초기화 실행 전 Railway PostgreSQL 백업 또는 수동 스냅샷을 권장하지만, 백업 생성 여부가 API 실행을 자동 차단하지는 않는다.
- 초기화 직후 관리자 계정의 로그인 유지, 빈 랭킹, 지급된 티켓, 뽑기 가능 여부 및 과거 5성 로그 제거를 확인한다.

## 비목표

- 과거 시즌 데이터 보관 또는 복원
- 시즌 이름, 번호, 시작·종료일 관리
- 카드 콘텐츠나 관리자 게임 설정 초기화
- 카드 이미지 파일 삭제
- Discord 반디봇의 JSON 메모리 초기화
- 다른 Railway 서비스 또는 같은 PostgreSQL 안의 비카드 스키마 변경
